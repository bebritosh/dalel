# DÄLEL — принятые решения

Журнал решений по прототипу. Пишем причину, а не только факт.

## 10 ключевых решений (с причинами)
1. **PaddleOCR убрали, оставили Tesseract за интерфейсом `OcrEngine`.** На Windows + Python 3.14 paddlepaddle не ставится готовыми колёсами. Интерфейс позволяет добавить вторую реализацию позже без переписывания.
2. **PDF обрабатываем через PyMuPDF (`pymupdf`).** Один пакет и для встроенного текста, и для растеризации, без внешнего Poppler — меньше зависимостей на Windows.
3. **`FixtureProvider` — режим по умолчанию (`LLM_MODE=fixture`).** Демо и тесты работают офлайн и детерминированно; живой Anthropic включается переменной окружения.
4. **Pydantic-схемы отдельно от SQLModel-моделей** (`app/schemas` vs `app/models`), роутеры тонкие, бизнес-логика в `app/services`. Чистые слои, тестируемость.
5. **Хранилище:** SQLite в `data/`, файлы в `data/cases/{case_id}/{uuid}.{ext}`; имена файлов только uuid. Тесты — на временной БД и папке. Приватность и изоляция тестов.
6. **Аутентификация:** один `access_token` на дело, сверка заголовка `X-Case-Token`, несовпадение → 404 (не раскрываем существование дела). Логин/пользователи для MVP избыточны.
7. **PDF-экспорт — опциональная деградация:** всегда DOCX; PDF только при наличии LibreOffice. На демо LibreOffice нет → PDF вырезан.
8. **Правовые нормы — только заглушки** в `rules/legal_refs.json` с пометкой `unverified: needs lawyer review`, без выдуманных номеров статей; в тексте — «[норма уточняется юристом]». Нельзя выдавать догадки за право.
9. **У `Fact` есть поле `grounded`** отдельно от `confirmed_by_user`. Grounding (значение найдено в строках чека) должен оставаться честным даже после ручного подтверждения пользователем.
10. **Проверки и «недостающее» считаются на лету** в GET-эндпоинтах; события (`Event`) персистятся. Простее поддерживать актуальность после правок полей, без кэша.

## Что вырезано и почему
- **PaddleOCR** — не ставится на Windows/3.14 (см. решение 1).
- **Проверки V5–V8** — для MVP оставлены V1–V4 (значение в источнике, корректность/непротиворечивость даты, сумма = сумме позиций, порядок покупка→обращение→отказ).
- **dark mode** — не заявлен в `frontend/docs/design.md`, вне рамок.
- **Распознавание дефекта/«реальности» фото** — вне рамок; фото-проверки оценивают только пригодность снимка (Шаг 8).

> **Пересмотрено в автономной работе 25.11 (Шаги 2–12).** Раньше были вырезаны и теперь реализованы:
> - **Telegram JSON-парсер** — реализован (Шаг 4), события из `.txt` и `.json` в общей хронологии (Шаг 5).
> - **PDF-экспорт** — реализован опционально через LibreOffice (Шаг 7); без `SOFFICE_PATH`/soffice → 503, не ошибка.
> - **Видео дефекта (mp4)** — принимается как доказательство `kind=photo` (Шаг 9), без анализа.

## Что исправлено по ходу
- **SQLModel на Python 3.14:** убрали `from __future__ import annotations` в таблицах (строковые аннотации не резолвились в классы) и перешли на tz-aware `datetime` (этот sqlmodel хранит `UTCDateTime` и требует timezone). Иначе падали создание таблиц и INSERT.

## Фикстуры: что откуда и почему это важно
- **`eval/fixtures/{sha}.layout.json`** — это **разметка генератора чека** (истинные строки и bbox), а **НЕ** вывод реального OCR. Нужна, чтобы демо было офлайн и детерминированным. Нельзя показывать как «результат распознавания».
- **`eval/fixtures/handmade_{sha}.json`** — **рукописный** ответ извлечения (на демо нет ключа LLM). Помечен префиксом `handmade_` и полем `_source: "handmade_no_live_llm"`. Нельзя выдавать за реальный ответ модели.
- Реальные ответы живого режима сохранялись бы как `{sha}.json` (без префикса). Провайдер фикстур сначала ищет `{sha}.json`, затем `handmade_{sha}.json`.
- Все демо-данные (названия магазина, суммы, даты, имена в переписке) **полностью вымышлены**.


## Блок 2: живое извлечение и режим `auto`
- **Провайдеры** за одним интерфейсом `LlmProvider`: `OpenAiProvider` (httpx, Chat Completions, `response_format=json_schema`, `strict: true`, `max_completion_tokens`; `max_tokens` устарел), `LiveProvider` (Anthropic, по умолчанию `claude-sonnet-5-5`; прежний ID `claude-opus-4-8` был неверным), `RuleBasedProvider` (**rule-based baseline**, не LLM), `FixtureProvider`. Строгая схема OpenAI: все поля `required`, `additionalProperties: false`, необязательные значения как `type: [..., "null"]`.
- **Ошибки:** невалидный JSON/схема → один повтор, затем `OpenAiError` без содержимого чека; HTTP-ошибки сообщают только код. Тело запроса, текст OCR и ключ не логируются.
- **`LLM_MODE=auto` управляет и OCR, и извлечением** (одна ручка вместо двух): sha256 файла с `*.layout.json` → фикстурный OCR; иначе Tesseract. Извлечение: фикстура только если есть и layout-, и extraction-фикстура (иначе номера строк не совпали бы с живым OCR); иначе OpenAI при наличии ключа, иначе rule-based baseline. `OCR_ENGINE=auto` тоже допустим.
- **Происхождение данных:** у `Document` два поля `ocr_source` (`fixture|tesseract`) и `extract_source` (`fixture|openai|anthropic|rules`), отдаются в `DocumentRead`; UI показывает плашку источника. (Ранее требовалось вручную удалять `data/dalel.db`; снято в Шаге 2 авто-миграцией.)
- **`SAVE_LLM_FIXTURES=1`** (по умолчанию выкл.) сохраняет ответ openai/anthropic как `eval/fixtures/{sha}.json` для офлайн-повтора; только для синтетических чеков.

## Автономная работа 25.11 (Шаги 2+)

### Шаг 2: стабильность БД и миграция Event
- **Авто-миграция вместо «удалить БД».** На старте (`create_db_and_tables`) после `create_all` вызывается `reconcile_columns()`: сравнивает колонки моделей с реальной схемой SQLite и добавляет недостающие через `ALTER TABLE ADD COLUMN`. Неразрушающе — только добавление, данные сохраняются. Требование удалять `data/dalel.db` снято.
- **Почему не Alembic:** новых зависимостей не вводим; для прототипа на SQLite достаточно идемпотентного `ADD COLUMN`. Удаление/переименование колонок ADD COLUMN не покрывает — для этого есть `scripts/reset_db.py` (явный разрушающий сброс с подтверждением).
- **NOT NULL на непустой таблице:** SQLite запрещает `ADD COLUMN ... NOT NULL` без default на непустой таблице. `_default_literal` берёт python-default колонки (`""`, `0`, `1`) или дефолт по типу; если литерал вывести нельзя — колонка добавляется как nullable, а не падает.
- **`Event.message_id`** (строка, nullable) добавлено той же миграцией — нужно Шагу 5 (ссылка события на сообщение-источник; без источника событие не создаётся). `document_id` в `Event` уже был.
- Тесты: `tests/test_migration.py` (старая схема → колонки добавлены, данные целы; повторный прогон — пусто). Итог прогона: **52 passed**.

### Шаг 5: события из чата через словарь
- **`rules/chat_events.yaml`** хранит ключевые фразы отказа; детект событий (`detect_events`) читает их, без модели. Виды: `contact` (первое сообщение покупателя), `reply` (первое сообщение продавца, если оно не отказ), `refusal` (первое сообщение продавца с фразой отказа).
- **Новый вид `reply`** добавлен в `EventKind`, схему `EventRead`, TS-тип `EventKind`, i18n (ru/en) и порядок timeline. Если продавец отказывает сразу, `reply` не создаётся (отказ его замещает).
- **Источник обязателен:** событие создаётся только из сообщения с `message_id`; `DetectedEvent.message_id` прокидывается в `Event.message_id`. Сообщение без id событием не становится.
- **Два источника:** `timeline.build_events` маршрутизирует документ-переписку по расширению: `.txt` → WhatsApp, `.json` → Telegram; события обоих попадают в общую хронологию, сортировка по дате.
- Все события `needs_review=true`. Тесты: reply до отказа, нет reply при мгновенном отказе, message_id у событий, нет события без источника.

### Шаг 6: контроль DOCX
- **Guard по итоговому тексту DOCX.** `export_docx` после рендера извлекает текст готового файла (`_docx_text`) и повторно прогоняет `check_text` по нему, а не только по исходному `build.text`. Рассинхрон шаблона и контекста больше не протащит неподтверждённое число/дату.
- **Нет пустых плейсхолдеров.** Если в финальном тексте остались маркеры `{{ }}`/`{% %}` — `ExportError` (HTTP 500), это баг шаблона, а не ошибка пользователя.
- Тесты: нет маркеров в реальном DOCX; подмена суммы в контексте ловится guard’ом по финальному тексту; маркеры в значении поля → `ExportError`.

### Шаг 7: PDF через LibreOffice
- **PDF = DOCX → LibreOffice headless.** `export_pdf` рендерит тот же guard’ованный DOCX и конвертирует его `soffice --headless --convert-to pdf`. Отдельного PDF-рендера нет — один источник истины, те же проверки.
- **Поиск soffice:** `SOFFICE_PATH` из `.env` → `PATH` → стандартные пути установки. Не найден → `SofficeUnavailableError` → **HTTP 503** с понятным текстом (не падение). PDF-кнопка на фронте покажет этот текст (Шаг 10).
- **Пересмотр решения:** ранее PDF был вырезан (DOCX достаточно). Теперь PDF поддержан опционально; отсутствие LibreOffice — ожидаемое 503, а не ошибка.
- Неизвестный формат экспорта → 400. Тест конвертации помечен `skip`, если soffice не установлен (на этой машине — skip).

### Шаг 8: проверки фото (Pillow)
- **Только Pillow, без OpenCV.** `photo_checks.check_photos`: P1 разрешение (min side), P2 размытость (`ImageFilter.FIND_EDGES` + дисперсия яркости краёв `ImageStat`), P3 экспозиция (средняя яркость вне диапазона), P4 EXIF-дата съёмки раньше даты покупки. Пороги — в `rules/validation.yaml` (P1–P4).
- **Всё — warning, не блок.** Проверки информируют пользователя; claim/export не блокируются (guard отдельно). EXIF-дата даёт P4 на ревью, а не ошибку.
- **Распознавания дефекта нет** — оцениваем только пригодность снимка, не содержание.
- **Поворот по EXIF уже был** в `ocr/preprocess.py` (`ImageOps.exif_transpose`) до OCR — не дублируем. **M3 уже по `kind=photo`** в `missing.py` — не меняем.
- `CheckResult.document_ids` добавлено (ссылка на фото); TS-тип обновлён. mp4 и нечитаемые файлы пропускаются (анализируются только .jpg/.jpeg/.png).

## Исправление DOCX «содержимое не удалось прочитать» (Часть 1)
**Причина.** OCR может отдавать управляющие символы (U+0000–U+001F, кроме `\t \n \r`), недопустимые в XML 1.0. Если такое значение (например, имя продавца или название товара из распознавания) попадает в претензию, оно уходит в `word/document.xml`: fallback-путь на `python-docx` падает с `ValueError: All strings must be XML compatible`, а в шаблонном пути символ может сохраниться в XML, и Word откажется открывать файл («содержимое не удалось прочитать»). Спецсимволы `& < >` docxtpl экранирует сам, но управляющие символы не экранируются ничем — их нужно удалять. **Фикс:** одна функция `_xml_safe` в `app/services/claim.py` вычищает недопустимые XML-символы из всех строковых значений (продавец, товары, валюта) **один раз в `build_claim`, до подстановки** — покрывает и шаблонный, и fallback-путь. Числа и даты переформатируются из нормализованных значений и чистки не требуют; guard и инварианты не затронуты (управляющие символы не влияют на числа/даты). Тесты: DOCX с управляющими символами во входных данных парсится всеми XML-частями, открывается `python-docx`, текст продавца сохранён без мусора; подмена суммы по-прежнему даёт 422.

## Дизайн: экран претензии (Часть 2)
**Команды Impeccable — что реально установлено.** Отдельных слэш-команд `/audit`, `/critique`, `/normalize`, `/polish`, `/clarify`, `/harden` в этом окружении **нет** — они не зарегистрированы как вызываемые команды. Impeccable присутствует как **автоматический design-хук** (`impeccable@1`): он прогоняется на каждом изменении `.tsx` и проверяет детерминированные проблемы вёрстки/дизайна (на правках `ClaimSummary.tsx`, `ClaimPage.tsx`, `Timeline.tsx`, `UploadPage.tsx` — «No deterministic design-quality issues found»). Из дизайн-скиллов доступны `design:design-critique`, `design:accessibility-review`, `design:ux-copy`, `design:design-system`, `design:design-handoff`. Проходы audit/critique/normalize/polish выполнены вручную по `frontend/docs/design.md` (токены, 8px-сетка, ширина 1120px, радиус 12px, одна главная кнопка, дисклеймер в шапке).

**Что изменено (только вёрстка/стили, текст претензии/числа/даты/id токенов не тронуты).** Добавлен компонент `ClaimSummary` — сводная карточка над текстом претензии: итоговая сумма требования в плашке `--highlight` с обводкой `--highlight-border` (визуальный акцент), продавец и дата покупки, явный статус «подтверждено» (`StatusBadge`), и блок «Источники» с чипами документов (Чек/Переписка) и плашкой происхождения (`ProvenanceBadge`, OCR/Извлечение). Все значения берутся из подтверждённых фактов (`data.facts`), claim-текст и токены не меняются. Адаптив: на 1440 — строка, на 390 — колонка без горизонтальной прокрутки. Пустые состояния (нет токена/нужно подтвердить), ошибки (`ErrorBox`) и статусы (текст+цвет, не только цвет) уже были и сохранены.

## 26.11
- **Правовые нормы из первоисточника.** Нормы в `rules/legal_refs.json` вписаны только после сверки с официальным текстом Закона РК от 4 мая 2010 года № 274-IV на adilet.zan.kz (редакция с изменениями от 19.06.2026 № 320-VIII). В каждой записи: `citation`, `text`, `source_url`, `checked_at`, `lawyer_reviewed=false`. Модель их по-прежнему не пишет; претензия копирует `citation` и `text` дословно. Юрист должен подтвердить формулировки (см. LAWYER_QUESTIONS.md).
- **Guard и номера статей.** Номера статей не являются фактами, поэтому guard вырезает из текста перед проверкой **только точные строки `citation` из файла**. Любая другая ссылка («ст. 99 …») и любое число рядом со ссылкой по-прежнему блокируют экспорт (тест).
- **Срок ответа 10 календарных дней** — теперь со ссылкой на п. 2 ст. 42-4, а не «по умолчанию, уточняется».
- **Mock-экспорт = настоящий файл.** Сборка без бэкенда раньше отдавала текст с расширением `.docx` — Word закономерно ругался. Теперь `scripts/make_mock_exports.py` гоняет настоящий бэкенд на синтетическом demo-001 и кладёт DOCX/PDF в `frontend/public/mock/`, текст — в `frontend/src/mock/claimText.ts`; тест падает, если текст разошёлся с бэкендом.
- **Tesseract psm 6.** На фото чека с правой колонкой сумм psm 3 разносил «ИТОГО:» и сумму в разные блоки. psm 6 держит строку целиком; на 9 старых делах без регрессий в openai, в rules — минус товары (regex-база). Правка «TOO»→«ТОО» — только для префикса в начале строки, как и второй проход для KZT: это постобработка OCR, не догадка.
- **Реалистичная синтетика вместо реальных чеков.** Реальные чеки в OpenAI не отправляем (персональные данные, нет согласия и DPA). Фото-синтетика case-010..015 закрывает разрыв «чистая картинка vs фото с телефона» без персональных данных.

## Убраны ложные статусы «отправлено» (26.11)

Таймер срока ответа продавца оставлен (реальная функция: пользователь отмечает, что сам отправил, — начинается отсчёт по ст. 42-4). Инварианты (числа/даты/текст претензии/guard/`confirmed_by_user`) не трогались; изменены только подписи.

- **Правки казахского черновика:** «Нені жетіспейді» → «Не жетіспейді» (грамматика); «Қосымша ештеңе жібермейді» → «DÄLEL өзі ештеңе жібермейді» («қосымша» значит и «приложение», и «вложение» — в блоке про вложения это двусмысленно). Новые KK-тексты M1–M5 и событий — тоже черновик для проверки носителем.
- **Казахские чеки, извлечение по правилам.** Итог: «ЖИЫНЫ», «ЖИЫНТЫҒЫ», «БАРЛЫҒЫ» (сильные, как ИТОГО), «ТӨЛЕУГЕ» (слабый, как «к оплате»); валюта «теңге»; служебные строки БСН/ЖСН, «Ауысым», «Күні», «Рахмет», ФБ/ФДО не считаются товаром. Tesseract без казахской модели читает Ғ как Г/РГ, Ө как О/Е, Ң как Н — эти варианты тоже учтены (тесты на «БАРЛЫРГЫ», «Барлыгы», «Кун1»).
- **Привязка валюты.** Валюта хранится кодом KZT, а на чеке может быть «₸», «тг», «тенге», «теңге». Раньше KZT без буквального «KZT» в строке считался непривязанным («не найдено дословно»). Теперь для KZT любое из этих написаний в указанной строке — привязка; eval считает так же (OCR-recall и галлюцинации по валюте).
- **`OCR_LANGS` не меняли.** Казахская модель Tesseract уже стоит, но `rus+kaz+eng` ухудшает русские фото-чеки (rules, 15 дел: продавец 93→87%, товар 37→30%). По умолчанию остаётся `rus+eng`; казахские чеки и так распознаются (итог 2/2 на обоих наборах языков). Возможный следующий шаг — второй проход с `kaz`, если в тексте есть казахские маркеры (БСН, ЖШС, ЖИЫНЫ).
- **Eval (rules, `rus+eng`), казахские case-016..017, до → после:** сумма 0/2 → 2/2; валюта 1/2 → 2/2; дата 2/2 → 2/2; продавец 1/2 → 1/2 (OCR читает «Сәрсенбаев» как «Сэрсенбаев»); товары 0/2 → 0/2 (общая проблема формата «1 x цена = сумма», как на русских фото-чеках); привязка 5/6 → 8/8; галлюцинации 1 → 0; guard n/a → 2/2. 15 прежних дел — построчно без изменений.
